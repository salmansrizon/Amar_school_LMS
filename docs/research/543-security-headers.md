## 1. Verdict up front

| Question | Answer |
|---|---|
| Nonce or hash? | **Nonce**, in `proxy.ts`. Hash-based needs `experimental.sri`, which is experimental and App-Router-only, and buys back static generation this app does not use. |
| How does the nonce reach streamed RSC? | Automatically — but only if the proxy sets `Content-Security-Policy` on the **request** headers, not just the response. Next parses it server-side and stamps every framework/bundle/inline tag it emits. |
| Supabase `connect-src`? | `https://<ref>.supabase.co` **and** `wss://<ref>.supabase.co`. Derive from `NEXT_PUBLIC_SUPABASE_URL`, never hardcode. |
| `frame-ancestors` enough? | Yes per ASVS 5.0 §3.4.6 — but keep `X-Frame-Options: DENY` anyway, and note that `frame-ancestors` **does nothing in report-only mode**, so it must ship enforced from day 1. |
| Biggest stack-specific trap | `img-src 'self'` **breaks every private image in the app** (12 signed-URL redirect routes → Supabase Storage). See §3.2. |
| Second biggest trap | A nonce **cannot** authorise a `style="…"` attribute. React SSR emits those. Needs `style-src-attr 'unsafe-inline'`. See §3.3. |
| Rollout | Enforced minimal CSP + `Content-Security-Policy-Report-Only` strict CSP, both at once, flipped by one env var. See §5. |

## 2. Nonce vs hash with the App Router

### 2.1 What the Next.js guide actually prescribes

The [Next.js CSP guide](https://nextjs.org/docs/app/guides/content-security-policy)
(v16.3.3 doc, last updated 2026-03-20) gives exactly one recommended shape: generate a
nonce per request in `proxy.ts`, put it in the CSP header, and *also* set the CSP header
on the forwarded **request** headers:

```ts
const requestHeaders = new Headers(request.headers)
requestHeaders.set('x-nonce', nonce)
requestHeaders.set('Content-Security-Policy', contentSecurityPolicyHeaderValue)

const response = NextResponse.next({ request: { headers: requestHeaders } })
response.headers.set('Content-Security-Policy', contentSecurityPolicyHeaderValue)
```

Setting it on the request is not decoration. Quoting the guide's "How nonces work in
Next.js":

> 1. **Proxy generates a nonce** … adds it to your `Content-Security-Policy` header, and
>    also sets it in a custom `x-nonce` header.
> 2. **Next.js extracts the nonce**: During rendering, Next.js parses the
>    `Content-Security-Policy` header and extracts the nonce using the `'nonce-{value}'`
>    pattern.
> 3. **Nonce is applied automatically**: Next.js attaches the nonce to: Framework scripts
>    (React, Next.js runtime); Page-specific JavaScript bundles; Inline styles and scripts
>    generated by Next.js; Any `<Script>` components using the `nonce` prop.

### 2.2 How the nonce reaches streamed RSC payloads

This is the part the ticket asks about, and it is answered by step 3 above: the streamed
RSC flight payload arrives in the document as a sequence of Next-generated inline
`<script>` chunks. Because Next itself emits those tags during SSR, and because it read
the nonce off the request-side CSP header before rendering started, **every one of those
chunks is stamped with the nonce, including the ones flushed after the initial shell**.
There is no per-component work, no `useNonce`, and no need to thread anything through
Suspense boundaries. The guide is explicit: "Because of this automatic behavior, you don't
need to manually add a nonce to each tag."

The corollary is the failure mode: if you set the CSP on the response only (the obvious
mistake), rendering never sees a nonce, Next emits unstamped inline scripts, and the
hydration bootstrap is blocked — the page renders and then is dead. This is why the
request-header line is mandatory, not stylistic.

`'strict-dynamic'` in `script-src` is what lets the nonced bootstrap script go on to load
the code-split chunks it pulls in without each chunk URL being allowlisted. Keep it.

### 2.3 Why not hash-based / SRI

The guide documents an alternative: `experimental.sri: { algorithm: 'sha256' }`, which
adds build-time `integrity` attributes and lets you drop the nonce and keep static
generation. Its own "Limitations" list rules it out here:

> * **Experimental**: Feature may change or be removed
> * **App Router only**: Not supported in Pages Router
> * **Build-time only**: Cannot handle dynamically generated scripts

The trade it buys — static generation and CDN caching — is a trade this app cannot bank
anyway. Every authenticated route already reads cookies via `@supabase/ssr` and is
therefore dynamic, and staging already sends `private, no-store` on authenticated pages.
The guide's warning that nonces disable static optimisation, ISR and PPR costs this app
nothing on `/school`, `/student`, `/super-admin`, `/distributor`. It *does* cost something
on the public apex marketing/login pages, which is the one place worth measuring after
rollout.

Verdict: **nonce**. Revisit SRI only if `experimental.sri` graduates and the public pages
become a measured problem.

## 3. What this app actually needs in each directive

Derived by reading the repo, not by copying a snippet.

### 3.1 `connect-src` — Supabase auth, PostgREST, Storage, Realtime

Supabase's browser client talks to exactly one origin, the project origin, over two
schemes:

- **HTTPS** — `https://<PROJECT_REF>.supabase.co`. Covers GoTrue auth (token refresh,
  sign-in/out from Client Components), PostgREST queries, and Storage uploads. The repo
  does browser-side Storage uploads in `app/student/tasks/[id]/submit-work.tsx` and
  `app/student/profile/correction-form.tsx`, so this is not optional.
- **WSS** — `wss://<PROJECT_REF>.supabase.co/realtime/v1/websocket`. Per the
  [Realtime Protocol doc](https://supabase.com/docs/guides/realtime/protocol):
  > To start the connection we use the WebSocket URL, which for: Supabase projects:
  > `wss://<PROJECT_REF>.supabase.co/realtime/v1/websocket?apikey=<API_KEY>`

  Grepping the repo for `.channel(` returns **zero hits** — Realtime is not used today.
  Include the `wss:` origin anyway: it is one token, it is the same host already trusted
  over HTTPS, and leaving it out converts the first future `.channel()` call into a
  silent production-only failure.

`ws:`/`wss:` are **not** covered by an `https:` host-source — the scheme must match, which
is why both entries are listed.

Also needed in `connect-src`: `'self'` (Server Action POSTs, RSC navigations, the
`/api/*` signed-object routes).

Not needed: `esms.mimsms.com` and `api.resend.com` appear in the repo but are called
**server-side only** (SMS and email). Server-to-server fetches are outside CSP entirely.

### 3.2 `img-src` — the trap that would break every private image

`web/lib/storage/signed-object.ts` is the shared seam behind twelve `/api/*` routes
(`school-logo`, `student-photo`, `gallery-photo`, `publication-image`,
`accounting-attachment`, `syllabus`, …). Its last line:

```ts
return NextResponse.redirect(signed.signedUrl)
```

So `<img src="/api/school-logo">` is a **cross-origin redirect** to
`https://<ref>.supabase.co/storage/v1/object/sign/…`. CSP evaluates redirect targets:
CSP3's source-list matching carries a *redirect count* parameter precisely so that it can
relax **path** matching after a redirect while still requiring the scheme/host to match
(CSP3 §6.7.2.7, §7.6 "Paths and Redirects"). A same-origin-only `img-src 'self'` therefore
blocks the redirected fetch.

Consequence if this is missed: every school logo, student photo, gallery image,
publication image — and every **print view header**, which uses the same logo route
(`components/print/pieces.tsx`, `app/api/school-logo/route.ts`, issue #92) — silently
renders as a broken image. The print views are the highest-visibility casualty and the
least likely to be caught by a smoke test.

So: `img-src 'self' data: blob: https://<ref>.supabase.co`.

(`data:` and `blob:` are in the Next guide's baseline and are needed for `next/image`
placeholders and client-side file previews.)

> Confirm empirically during the report-only phase (§5) — this is the single claim below
> that I could not pull verbatim from the CSP3 text (the W3C page truncated on fetch).
> Including the origin is correct either way; the report-only phase decides whether it was
> load-bearing.

### 3.3 `style-src` — a nonce cannot authorise a `style="…"` attribute

Tailwind v4 compiles to a real stylesheet served from `/_next/static`, so `style-src
'self'` covers the bulk. Two things do not fit:

1. **Next-generated inline `<style>` blocks** (critical CSS, `next/font` fallback metrics)
   — these are covered, because Next stamps them with the nonce (guide, step 3).
2. **`style="…"` HTML attributes.** `style-src-attr` (falling back to `style-src` when
   absent) governs these, and there is nowhere to put a nonce on an attribute — nonces are
   simply not a mechanism that can allow them. The repo has four `style={{…}}` usages in
   `app/`/`components/`, and React SSR renders each as a literal `style` attribute.
   `@base-ui/react` popovers/tooltips and `sonner` toasts add more.

Runtime CSSOM writes (`el.style.left = x`, which is how React *updates* styles on the
client) are unaffected by CSP. Only markup attributes are. So the SSR pass is what breaks.

Minimal fix: `style-src 'self' 'nonce-{n}'; style-src-attr 'unsafe-inline'`. Splitting the
directive keeps `'unsafe-inline'` off inline `<style>` **elements**, which is where the
real injection risk is; inline style *attributes* are a weak vector and this is the
standard trade. The alternative — deleting four `style={{}}` sites and patching
`@base-ui/react` — is not worth it. Do not fall back to a blanket `style-src 'self'
'unsafe-inline'`; that is strictly worse for the same convenience.

### 3.4 `font-src` — nothing external

`app/layout.tsx` uses `next/font/google` (`Plus_Jakarta_Sans`, `Hind_Siliguri`). Per the
[production checklist](https://nextjs.org/docs/app/guides/production-checklist), the Font
Module "automatically hosts your font files with other static assets, **removes external
network requests**". So `font-src 'self'` — no `fonts.gstatic.com`.

### 3.5 `form-action` — Server Actions

Server Actions POST to the same origin, so `form-action 'self'` is sufficient. Worth
stating explicitly because `form-action` does **not** inherit from `default-src`; omitting
it leaves form submissions entirely unrestricted.

### 3.6 Print views (ADR 0007) — no extra surface

Browser-native print is `window.print()` on the already-rendered document plus
`@media print` rules in `app/globals.css`. No worker, no `blob:` PDF, no wasm — grep for
`new Worker`, `serviceWorker`, `createObjectURL` returns nothing. The only CSP-visible
part of a print view is the school logo `<img>`, i.e. §3.2. No `worker-src`,
no `'wasm-unsafe-eval'`.

### 3.7 `dangerouslySetInnerHTML` — two sites, both SVG

`app/school/students/[id]/print/id-card/page.tsx:84` and `components/print/pieces.tsx:255`
inject QR-code SVG markup. Inline SVG is markup, not a fetched resource, so CSP does not
gate it — but any `<script>` inside would be caught by `script-src`. Both inputs are
locally generated by `qrcode`, so this is fine today; it is the standing ASVS **V1.3.1**
item (§6) to keep it that way.

## 4. `frame-ancestors` vs `X-Frame-Options`

Three sources, one conclusion, with one timing caveat.

- **ASVS 5.0 §3.4.6 (L2)** is the strongest statement — it names XFO as unusable:
  > Verify that the `frame-ancestors` directive of the `Content-Security-Policy` header
  > field … cannot be embedded by default … the `X-Frame-Options` header field … **is
  > obsolete and may not be relied upon**.
- **MDN `frame-ancestors`**: "Baseline **Widely available**", "available across browsers
  since January 2018", and setting it to `'none'` "is similar to `X-Frame-Options: deny`
  (which is also supported in older browsers)".
- **MDN `X-Frame-Options`**: recommends `frame-ancestors` for "more comprehensive
  options"; flags `ALLOW-FROM` as obsolete with `frame-ancestors` as the replacement.

**Recommendation:** `frame-ancestors 'none'` is the control of record. Ship
`X-Frame-Options: DENY` alongside it anyway — it is one static header, it costs nothing,
and it covers the pre-2018 tail. Do not treat XFO as the protection.

**The timing caveat that changes the rollout:** a `frame-ancestors` directive delivered in
`Content-Security-Policy-Report-Only` is not enforced — report-only, by definition,
reports and does not block. If the whole CSP ships report-only first, the app has **no
clickjacking protection at all** during the observation window. Hence the split rollout in
§5: `frame-ancestors 'none'` goes out **enforced** on day 1 in a minimal policy, while the
strict script/style policy rides along in a separate report-only header. Both headers may
be sent simultaneously; that is what report-only is for
([Vercel](https://vercel.com/docs/cdn-security/security-headers): "Before enforcing a CSP,
start with the `Content-Security-Policy-Report-Only` header").

## 5. Report-only rollout path

The goal is that a wrong policy cannot silently break production, and that a rollback is
an env change rather than a deploy.

### Phase 0 — static headers + enforced clickjacking (no risk)

Ship `next.config.ts` `headers()` with HSTS/nosniff/Referrer-Policy/XFO/COOP,
`poweredByHeader: false`, and an **enforced** `Content-Security-Policy:
frame-ancestors 'none'` (that directive alone, nothing else). Nothing here can break a
page render. Verifiable with `curl -sI`.

### Phase 1 — report-only strict policy on staging

Add the nonce plumbing to `proxy.ts` and emit the full strict policy under
`Content-Security-Policy-Report-Only`, keeping the Phase-0 enforced header. Wire reporting
per MDN, which is explicit that the directive is mandatory:

> The CSP `report-to` directive must be specified for reports to be sent: if not, the
> operation won't have any effect.

```
Reporting-Endpoints: csp-endpoint="/api/csp-report"
Content-Security-Policy-Report-Only: …; report-to csp-endpoint
```

`/api/csp-report` is a four-line route handler that `console.error`s the body — Vercel logs
are the dashboard. Do not build a violation UI.

Add `report-uri /api/csp-report` as well: it is deprecated in favour of `report-to`
(CSP3, MDN) but is still what several shipping browsers actually honour, and both may be
present.

### Phase 2 — drive the policy against real traffic

Walk `docs/testing/uat-plan.md` and the Playwright suite on staging with report-only on,
covering all five roles and — critically — every **print** route and every private-image
route, since §3.2 and §3.3 are exactly the violations that will show up. Tighten the
policy until the report stream is empty. Give it at least one full staging UAT cycle.

### Phase 3 — flip to enforcing

One env var chooses the header name; no code change, and rollback is a Vercel env edit
plus redeploy rather than a revert:

```ts
const header = process.env.CSP_MODE === 'enforce'
  ? 'Content-Security-Policy'
  : 'Content-Security-Policy-Report-Only'
```

Flip staging first, leave it a week, then production. Keep the report endpoint wired
after enforcement — an enforced CSP still reports, so the same stream now shows what is
being *blocked*.

## 6. Concrete header set

### 6.1 `web/next.config.ts` — static headers (apply everywhere, including assets)

```ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  reactCompiler: true,
  // ASVS 5.0 V13.4.6 — stop advertising the framework. Staging currently leaks
  // `x-powered-by: Next.js`.
  poweredByHeader: false,
  async headers() {
    return [
      {
        source: '/(.*)',
        headers: [
          // ASVS 5.0 V3.4.1 (L1/L2): >= 1 year AND all subdomains. The existing
          // staging value omits includeSubDomains, which fails at L2 — and this
          // app is multi-tenant on `*.edumebd.com`, so subdomains are the point.
          { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains; preload' },
          // ASVS 5.0 V3.4.4
          { key: 'X-Content-Type-Options', value: 'nosniff' },
          // ASVS 5.0 V3.4.5. `same-origin` because nothing here needs to send a
          // referrer off-site, and URLs carry student/exam/invoice ids.
          { key: 'Referrer-Policy', value: 'same-origin' },
          // ASVS 5.0 V3.4.6 says this is obsolete; kept as a pre-2018 backstop only.
          { key: 'X-Frame-Options', value: 'DENY' },
          // ASVS 5.0 V3.4.8 (L3), cheap to take.
          { key: 'Cross-Origin-Opener-Policy', value: 'same-origin' },
        ],
      },
    ]
  },
}

export default nextConfig
```

Skipped: `Permissions-Policy` — no ASVS 5.0 requirement, and the app uses no
camera/mic/geolocation. Add it when a feature needs one denied.

### 6.2 `web/proxy.ts` — the nonce'd CSP

The policy builder (new file or top of `proxy.ts`):

```ts
// Supabase lives on one origin over two schemes: HTTPS for auth/PostgREST/Storage,
// WSS for Realtime (unused today — listed so the first .channel() call is not a
// production-only surprise). Derived, never hardcoded, so preview/staging/prod and
// local Supabase all work.
const SUPABASE_ORIGIN = new URL(process.env.NEXT_PUBLIC_SUPABASE_URL!).origin
const SUPABASE_WS = SUPABASE_ORIGIN.replace(/^http/, 'ws')

export function cspFor(nonce: string) {
  const isDev = process.env.NODE_ENV === 'development'
  return [
    `default-src 'self'`,
    // 'strict-dynamic' lets the nonced bootstrap load its code-split chunks.
    // 'unsafe-eval' is dev-only: React uses eval to rebuild server error stacks.
    `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'${isDev ? " 'unsafe-eval'" : ''}`,
    // Nonce covers Next's inline <style> blocks (critical CSS, next/font metrics).
    `style-src 'self' 'nonce-${nonce}'`,
    // A nonce cannot authorise a style="..." ATTRIBUTE — React SSR emits those, and
    // so do @base-ui/react and sonner. Split out so 'unsafe-inline' never reaches
    // inline <style> elements, which is where the real risk is.
    `style-src-attr 'unsafe-inline'`,
    // Supabase origin is required: /api/school-logo & friends 302 to a signed
    // Storage URL, and CSP checks the redirect target. Without it every private
    // image AND every print-view header silently breaks.
    `img-src 'self' data: blob: ${SUPABASE_ORIGIN}`,
    `font-src 'self'`, // next/font/google self-hosts; no fonts.gstatic.com
    `connect-src 'self' ${SUPABASE_ORIGIN} ${SUPABASE_WS}`,
    `object-src 'none'`,            // ASVS V3.4.3
    `base-uri 'none'`,              // ASVS V3.4.3
    `form-action 'self'`,           // Server Actions; does NOT inherit default-src
    `frame-ancestors 'none'`,       // ASVS V3.4.6
    `frame-src 'none'`,
    `report-to csp-endpoint`,       // ASVS V3.4.7
    `report-uri /api/csp-report`,   // deprecated but still the one browsers honour
    `upgrade-insecure-requests`,
  ].join('; ')
}
```

Wiring it into the existing `proxy()`, which already builds responses in four places
(`NextResponse.next` twice, `rewrite` twice, `redirect` twice):

```ts
export async function proxy(request: NextRequest) {
  const nonce = crypto.randomUUID()
  const csp = cspFor(nonce)

  // The Next.js CSP guide advises not applying CSP to <Link> prefetches: a nonce
  // baked into a cached prefetch payload will not match the document that later
  // renders it. We cannot narrow the matcher the way the guide does — this proxy
  // must still run on prefetches for tenant + auth routing — so we skip only the
  // header injection.
  const isPrefetch =
    request.headers.get('next-router-prefetch') === '1' ||
    request.headers.get('purpose') === 'prefetch'

  // Rebuilt at each call site, NOT hoisted: the Supabase cookie setAll() mutates
  // request.cookies, and a Headers snapshot taken earlier would forward stale
  // auth cookies. Cloning late keeps the refreshed session intact.
  const fwd = () => {
    const h = new Headers(request.headers)
    if (!isPrefetch) {
      h.set('x-nonce', nonce)
      // Mandatory: Next reads the nonce off the REQUEST-side CSP header during
      // SSR. Response-only means unstamped inline scripts and a dead page.
      h.set('Content-Security-Policy', csp)
    }
    return { headers: h }
  }

  // ... existing body, with every
  //   NextResponse.next({ request })        -> NextResponse.next({ request: fwd() })
  //   NextResponse.rewrite(url)             -> NextResponse.rewrite(url, { request: fwd() })
  // (rewrites matter: /no-such-school and /account-blocked are rendered documents.)
  // Redirects need no nonce — no document is rendered.

  // On every returned response:
  //   const header = process.env.CSP_MODE === 'enforce'
  //     ? 'Content-Security-Policy'
  //     : 'Content-Security-Policy-Report-Only'
  //   if (!isPrefetch) {
  //     res.headers.set(header, csp)
  //     res.headers.set('Reporting-Endpoints', 'csp-endpoint="/api/csp-report"')
  //   }
}
```

Note the Phase-0 enforced `frame-ancestors 'none'` stays in `next.config.ts` for as long
as `CSP_MODE !== 'enforce'`, so clickjacking is covered throughout the report-only window.
Drop it from `next.config.ts` once the full policy is enforced, to avoid two enforced
CSP headers (which intersect, not override — harmless but confusing).

(L1 ⊂ L2 ⊂ L3). Proposal: **L2 is the release gate**, plus four L3s that are one-liners
here. The chapter that matters for this ticket is **V3 Web Frontend Security**; the
supporting ones are V1, V13, V7.

   and check whether the signed-URL redirect produces an `img-src` violation. This decides
   whether the Supabase origin in `img-src` is required or merely harmless.
2. **Measure the public pages.** Nonces force dynamic rendering. The authenticated app is
   already dynamic, but the apex marketing/login pages may lose static optimisation. If
   that shows up as a real TTFB regression, the escape hatch is a path-scoped policy
   (nonce on authenticated paths, `'self'`-only static policy on the apex) — not a weaker
   global policy.
3. **`@base-ui/react` / `sonner` inline styles.** §3.3 assumes `style-src-attr
   'unsafe-inline'` is enough. Report-only will confirm whether either library also injects
   an inline `<style>` element Next does not nonce.
4. **Supabase cookie attributes** (V3.3.1–V3.3.4) were not audited here; they are a
   read of `@supabase/ssr` cookie options, not a headers question.
