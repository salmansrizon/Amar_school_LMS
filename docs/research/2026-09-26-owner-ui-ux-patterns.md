# Owner UI/UX Patterns: DataTable, Drawer, Shortcuts

**Date:** 2026-09-26
**Scope:** How to build the School Owner redesign that has already been decided on. This covers the shared DataTable, the `?view=<id>` drawer, quick actions and alerts, and the `/`, `F` and `Esc` keys.
**Versions checked:** `next` 16.2.10, `@base-ui/react` 1.7.0 (`web/node_modules/*/package.json`).

## Recommendations

1. **Open the drawer with `window.history.pushState`, not `router.push`.** Next says native pushState/replaceState "integrate into the Next.js Router" and sync `useSearchParams` (`web/node_modules/next/dist/docs/01-app/01-getting-started/04-linking-and-navigating.md` §Native History API). Reading `searchParams` makes a page dynamic (`.../03-file-conventions/page.md`), so `router.push` would re-render the list page on the server on every open. *Tradeoff:* the drawer then fetches its record on the client, through a server action, with its own loading state. The docs do not say outright that pushState skips the RSC request, so **check this in DevTools (unverified)**.
2. **Push when opening. Close with `history.back()` if we pushed, otherwise `replaceState`.** When the drawer is already open, switching records (prev/next) should use replace. Back then closes the drawer. A cold deep link or refresh closes by removing `view` without leaving the app. *Tradeoff:* you need a small "did we push?" flag in memory.
3. **On refresh, have the page read `searchParams.view` on the server and render the drawer already open with data.** Refresh then shows the record straight away with no spinner. *Tradeoff:* the page load does one extra query.
4. **Do not use intercepting or parallel routes for this.** With them, the URL becomes `/students/123`, and on refresh "the entire photo page should render instead of the modal" (`.../03-file-conventions/intercepting-routes.md` L23). That breaks the requirement that refresh keeps the drawer open. It also needs an `@modal` slot plus `default.js` in each module. *Tradeoff:* you lose server-component drawer bodies. Recommendation 3 gets most of that benefit back.
5. **Use a controlled `Dialog` (`modal`, no `Dialog.Trigger`) styled as a right panel. Use `Drawer` only if you want swipe-to-dismiss on mobile.** base-ui's own Drawer docs say "a panel that slides in from the edge… and doesn't need gesture support is a positioned Dialog" (`web/node_modules/@base-ui/react/docs/react/components/drawer.md` L284). *Tradeoff:* with Dialog you get no swipe gesture. `Drawer` (stable since #4293, `CHANGELOG.md` L747) adds `swipeDirection="right"`.
6. **Set `finalFocus` explicitly.** Point it at the row's Profile button, and fall back to `#app-content` (`web/components/app-shell.tsx` L404) after a refresh, when no opener exists. By default focus returns to the "trigger or previously focused element" (`dialog.md` L3956). *Tradeoff:* each row's button needs a stable id.
7. **Build the table as a native `<table>`, not `role="grid"`.** Mark the sorted `<th>` with `aria-sort` and put a `<button>` inside it. Use a tri-state select-all checkbox. Put the ⋮ menu on base-ui `Menu`. Announce the selection count in `role="status"`. *Tradeoff:* each row costs about 3 tab stops (checkbox, Profile, ⋮). Keep the page size at 25 or below, or move to a grid later.
8. **Mobile cards: render two DOM trees from one state and hide one with CSS (`hidden md:table` and `md:hidden`).** An element with `display:none` is removed from the accessibility tree, so screen readers do not hear the list twice. Card mode drops the table semantics, so write each card as a `<li>` with a heading. *Tradeoff:* the markup doubles for 25 rows. Checkbox `id`s must differ between the two trees.
9. **Shortcuts: one `keydown` listener that returns early for editable targets, `isComposing`, `keyCode === 229`, any modifier key, or an open dialog. Match on `e.key`, not `e.code`.** Add a Settings toggle to turn single-key shortcuts off, which is what SC 2.1.4 requires. *Tradeoff:* users typing on a Bangla layout will not trigger `F` (that is the goal), but for them the shortcut does nothing.
10. **Follow the SIS norm: filter → checkbox → one "bulk action" menu.** Selection should persist across pages, as PowerSchool's does. Show record alerts as small typed icons that open detail. *Tradeoff:* keeping selection across server pagination means you store a set of ids, not row objects.

## Q1. SIS product patterns

- **Lists and bulk actions:** PowerSchool offers a header checkbox for "select all" or per-row checkboxes, then a "[Select Action]" menu. "Your checkbox selections are retained as you navigate through the different pages" ([Student Basic Search](https://ps.powerschool-docs.com/pssis-admin/latest/student-basic-search)). Classe365's flow is: filter Class/Section, tick the checkboxes, then pick from "the bulk action menu" ([bulk enroll](https://docs.classe365.com/en/articles/8753446-how-to-bulk-enroll-students-in-elective-or-flexi-core-subjects), [blocking users](https://docs.classe365.com/en/articles/9446886-classe365-blocking-users)). Gibbon uses "bulk-action checkboxes" in Reports ([search snippet of Gibbon docs](https://docs.gibbonedu.org/guides/modules/reports/publishing); page not fetched, so **unverified**).
- **Filters:** Fedena puts an "Advanced" button at the top right of Students, and it opens a separate Advanced Search page ([Fedena support](https://support.fedena.com/support/solutions/articles/212883-how-can-i-search-students-with-multiple-criteria-)). PowerSchool's main page has a scoped search with fields such as Grade Level and DOB, plus saved "Stored Selections" ([Main Page](https://ps.powerschool-docs.com/pssis-admin/latest/main-page)).
- **Side panel or full page:** In every product with public docs, clicking a name opens a **full record page**. In PowerSchool, clicking the name "opens their full student record page" (Basic Search, above). None of the documented products shows a side drawer. There is no evidence either way on drawers, so our choice stands on its own merits.
- **Alerts:** PowerSchool shows "an Alert icon at the top of each of [the student's] pages", typed as Birthday, Discipline, General, Guardian and Medical, and clicking one opens the details ([View Alerts](https://ps.powerschool-docs.com/pssis-teacher/latest/view-alerts)). Gibbon's profile shows "academic, behavioural, medical and SEN alerts… generated from system-wide data" ([Gibbon Students](https://gibbonedu.org/features/people/students/)).
- **Gaps:** Teachmint and openSIS help pages were not reachable (openSIS returned 403) or turned up only marketing and blog pages. I found **no primary evidence** on dashboard alert strips or quick-action rows in any of these products.

## Q2. Next.js 16 drawer and URL state

| Option | Refresh keeps drawer | Back closes | Server round-trip on open | Cost |
|---|---|---|---|---|
| `useSearchParams` + `history.pushState` | yes | yes | none per docs (verify) | client fetch |
| `useSearchParams` + `router.push(…, {scroll:false})` | yes | yes | yes, the dynamic page re-renders | list re-query |
| Intercepting + `@modal` parallel route | **no**, a full page renders (`intercepting-routes.md` L23) | yes (`parallel-routes.md` L226) | yes | slot + `default.js` per module (`parallel-routes.md` L265) |

- **Push or replace:** `router.push` "adds a new entry", while `replace` does so "without adding a new entry" (`.../04-functions/use-router.md` L44-45). The native methods behave the same way.
- **Scroll:** by default Next scrolls to the top on navigation, and you opt out with `scroll: false` (`use-router.md` L117-119). pushState does not scroll. The list scrolls inside `#app-content` (`app-shell.tsx` L404), and base-ui modal scroll-lock applies to the document (`dialog.md` L3783), so the list keeps its position.
- **Suspense:** a client component using `useSearchParams` in a prerendered route needs a `<Suspense>` boundary, or the production build fails (`use-search-params.md` L178-179). `cacheComponents` is off (`web/next.config.ts`), so the Activity guide does not apply.
- **Loading:** put a skeleton inside the drawer body. Keep the previous record visible while paging (React `useTransition`; this is not from the Next docs).

## Q3. base-ui Dialog as a drawer

- **Roles and ARIA:** Popup renders `role` (default `'dialog'`, `dialog/store/DialogStore.js` L83), `aria-labelledby` (from Title) and `aria-describedby` (from Description) (`dialog/popup/DialogPopup.js` L71-74). **It does not set `aria-modal`.** Instead it hides the rest of the page from assistive tech with `markOthers` (aria-hidden) (`floating-ui-react/components/FloatingFocusManager.js` L345). The APG asks for `aria-modal="true"` ([APG Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)), and hiding the outside content gets the same effect.
- **Focus:** the focus trap is built in when `modal` is true. On open, focus goes to the first tabbable element, or to the popup itself for touch input (`dialog.md` L3955). APG advises that for long content you focus a static heading so the top stays in view (APG Dialog), so set `initialFocus` to the Title ref. `finalFocus` is covered in Recommendation 6.
- **Esc:** handled for the topmost layer only (`dialog/root/useDialogRoot.js` L77), so a ⋮ menu inside the drawer closes first. With `modal` on, `<Dialog.Close>` must sit inside Popup "so touch screen readers can escape" (`dialog.md` L3783).
- **Controlled:** use `open` and `onOpenChange(open, details)`. The `details.reason` value includes `'escape-key'` (`dialog.md` L3778, L3810), which lets you route closing through Recommendation 2.
- **Repo state:** `components/modal.tsx` and `confirm-dialog.tsx` are custom-built, so the drawer will be the first base-ui Dialog.

## Q4. Accessible data tables

- **Element:** APG says "Authors are strongly encouraged to use a native HTML `table`". Grid is for tables that are mostly interactive widgets, because it cuts down tab stops ([APG Table](https://www.w3.org/WAI/ARIA/apg/patterns/table/)).
- **Sorting:** only the sorted `<th>` gets `aria-sort="ascending|descending"`. The header content is a `<button>`, the arrow icons are `aria-hidden`, and the explanation of sorting goes in the caption ([APG sortable table](https://www.w3.org/WAI/ARIA/apg/patterns/table/examples/sortable-table/)).
- **Select all:** it is tri-state, and when some rows are selected it reports `aria-checked="mixed"` ([APG Checkbox](https://www.w3.org/WAI/ARIA/apg/patterns/checkbox/)). A native `input.indeterminate` is the HTML equivalent (not covered on that APG page). Each row checkbox is labelled with the student's name.
- **Row ⋮ menu:** the button needs `aria-haspopup="menu"` and `aria-expanded`, and Enter, Space or ArrowDown opens it with focus on the first item ([APG Menu Button](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/)). Label it with the name, e.g. "More actions for Rahim".
- **Bulk announcements:** "12 selected" and the result of an action count as status messages under SC 4.1.3 ([Understanding 4.1.3](https://www.w3.org/WAI/WCAG21/Understanding/status-messages.html)). Keep one `role="status"` region always in the DOM.
- **Cards:** CSS `display` on table elements used to strip the table semantics. As of October 2023 this is fixed in Chromium and Safari 17, and mostly fixed in Firefox except `display:contents` ([Roselli, expert source](https://adrianroselli.com/2018/02/tables-css-display-properties-and-aria.html)). A single DOM restyled into cards would still read as "row 3, column Roll", which is wrong for cards. That is why Recommendation 8 uses two trees.

## Q5. Single-key shortcuts (SC 2.1.4)

- **Rule:** a shortcut that uses only printable characters must meet one of three conditions. It can be turned off, it can be remapped to include a non-printable key, or it is active only when its component has focus. Shortcuts with modifier keys are out of scope, so ⌘K is fine. The reason is speech input: someone dictating "Hey Kim" could trigger several commands ([Understanding 2.1.4](https://www.w3.org/WAI/WCAG21/Understanding/character-key-shortcuts.html)). `/` and `F` are page-wide, so **they need an off switch**. The alternative is remapping them to something like Alt+/.
- **IME:** skip the event if `event.isComposing || event.keyCode === 229`. `compositionstart` can fire after the first `keydown`, and in that case only `keyCode` is still 229 ([MDN keydown](https://developer.mozilla.org/en-US/docs/Web/API/Element/keydown_event)). `isComposing` became Baseline only in 2026 ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/isComposing)).
- **Bangla:** layout-based inputs such as Bijoy or Avro in fixed-layout mode emit Bangla characters for the `F` key, so matching on `e.key === 'f'` does not fire. Matching on `e.code === 'KeyF'` would fire. **Unverified:** the exact Bijoy key mapping, and whether Avro Phonetic reports composition events.
- **Editable targets:** skip `input`, `textarea`, `select`, any `[contenteditable]`, and any open `[role=dialog]` or `[role=menu]`.
- **Screen readers:** in browse mode, NVDA uses `f` to jump to the "next form field" and keeps the keystroke from the page. Pages only receive keys in focus mode (NVDA+Space) ([NVDA User Guide](https://download.nvaccess.org/documentation/userGuide.html)). So `F` will not reach our listener for NVDA users in browse mode, and that is harmless. Every shortcut therefore needs a visible button too. JAWS behaviour and Firefox's `/` quick-find are **unverified**. Calling `preventDefault` when we handle `/` should suppress quick-find.
